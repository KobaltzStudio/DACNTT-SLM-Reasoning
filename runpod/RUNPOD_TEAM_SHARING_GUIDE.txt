RUNPOD TEAM SHARING GUIDE Project: DACNTT-SLM-Reasoning Purpose: Shared
RunPod account, GPU Pod, Network Volume, and contribution tracking

1.  RECOMMENDED TEAM MODEL

Use one RunPod Team Account for the project. Each teammate should sign
in with their own RunPod identity and be invited to the Team. Do not
share one person’s password, MFA code, private SSH key, or personal API
key.

The Team Account owns the shared Pods, Network Volumes, and billing
context. A designated team administrator invites members and assigns the
least privilege role required.

Suggested roles (confirm exact current permissions in RunPod Console
before assigning): - Team owner / Admin: one project lead. Manages
members, billing configuration, Pods, and storage. - Dev: members who
need to create, start, stop, or manage Pods and volumes. - Basic:
members who only need access to assigned/shared running resources, where
supported. - Billing: person responsible for viewing/managing billing,
where supported.

Do not grant Admin to every teammate. Role names and permissions may
change; check the role description displayed by RunPod at invitation
time.

2.  CREATE OR CONVERT TO A TEAM

3.  Sign in at https://www.console.runpod.io/

4.  Open the account/team menu and locate Teams or the Team Account
    conversion option.

5.  Create/convert to a Team Account if the console offers that option.

6.  Use a clear project name, for example: DACNTT-SLM-Reasoning.

7.  Enable MFA for the owner and all members.

8.  Confirm who legally/financially owns the account and who is
    authorized to add funds.

Important: Do not create paid resources under an individual account and
assume they automatically become Team resources after conversion.
Confirm resource ownership and billing scope in the console first.

3.  INVITE TEAMMATES

4.  Open Team settings / Members.

5.  Select Invite member.

6.  Enter each teammate’s own RunPod account email.

7.  Assign the minimum role needed.

8.  Send the invitation.

9.  Each teammate accepts the invitation and switches to the project
    Team in the console.

Each teammate should verify that they are viewing the correct Team
before creating or managing resources.

4.  SHARED GPU POD WORKFLOW

Recommended initial shared setup: - One Pod only. - GPU: 1 x NVIDIA
L4. - Pricing: On-Demand, not Reserved. - Region: EU-RO-1, provided the
selected GPU and storage are available there. - Template: PyTorch 2.8.0,
subject to repository dependency validation. - Network Volume: one
shared project volume, mounted at /workspace. - Pod name:
kltn-dacntt-l4.

Only one designated operator should start/stop the Pod during a training
run. Other members can connect for monitoring or analysis only if their
role and connection method permit it.

Avoid having two people edit the same files or launch the same round
simultaneously. Use Git for source-code collaboration and a shared
volume for datasets/checkpoints/reports.

5.  SHARED STORAGE LAYOUT

Suggested layout on the Network Volume:

/workspace/ KLTN-SLM-Reasoning/ scripts/ config/ data/ models/task7/
reports/task7/ logs/task7/ huggingface/ backups/

Set Hugging Face cache to the persistent volume so models do not need to
be downloaded again after Pod recreation:

export HF_HOME=/workspace/huggingface export
HF_HUB_CACHE=/workspace/huggingface/hub

Keep source code in GitHub as the canonical version. The Network Volume
is for runtime data and experiment artifacts, not a replacement for Git.

6.  HOW TEAM MEMBERS CONTRIBUTE MONEY

RunPod billing is charged to the Team/account billing balance; it does
not automatically divide each invoice among teammates.

Recommended manual contribution process: 1. Agree on a total experiment
budget before adding funds. 2. Appoint one billing owner. 3. Create a
shared contribution ledger (Google Sheet or CSV) with: Date, member,
amount, currency, payment reference, RunPod credit added, current
balance, notes. 4. Each teammate transfers their contribution to the
agreed billing owner using a payment method agreed by the group. 5. The
billing owner adds credit to the RunPod Team Account. 6. Save the RunPod
receipt and record the amount in the ledger. 7. Record GPU hours and
storage charges after each experiment session. 8. Share a billing
summary with the team periodically.

Do not send payment-card details, passwords, MFA codes, SSH private
keys, or API tokens in the group chat.

Before pooling money, agree in writing: - Maximum contribution per
person. - Total spending cap. - Who can authorize additional top-ups. -
How unused balance is handled. - What happens if a member leaves the
project. - Whether expenses are split equally or by an agreed ratio.

7.  COST CONTROL

-   Prefer On-Demand over Reserved for this project.
-   Use one L4 Pod, not multiple simultaneous GPU Pods.
-   Stop the Pod when no GPU work is running.
-   Remember: stopping a Pod can stop GPU charges, but persistent
    Network Volume storage charges continue.
-   Do not terminate/delete the Pod until required artifacts are backed
    up and the volume is confirmed safe.
-   Check the live price shown in the console; prices and availability
    can vary by data center and time.
-   Start with a small pilot budget and measure one complete Cloud round
    before committing to all 18 rounds.

8.  DATA SAFETY AND BACKUP

At the end of each completed round: - Verify the adapter/checkpoint
exists. - Verify train_log.json exists. - Verify the dev evaluation
output and summary exist. - Run the relevant artifact/protocol
validator. - Copy important reports and logs to a second storage
location. - Record checksums for frozen input artifacts and important
outputs.

Do not assume tmux protects a process after the Pod is stopped or
terminated. tmux only protects against ordinary SSH disconnects while
the Pod itself remains running.

9.  TEAM OPERATING RULES

-   One person is the run operator for each GPU session.
-   Announce before starting or stopping the shared Pod.
-   Never launch the same seed/method/round twice concurrently.
-   Use Git commits to identify the exact source version used for an
    experiment.
-   Keep a run ledger: method, seed, round, start/end time, code commit,
    input hashes, output paths, status, GPU hours, notes.
-   Never overwrite completed experiment artifacts without a documented
    reason and explicit team approval.
