2. WHAT run_b4_b5.py DOES
======================================================================

Each command runs one method/seed/round through the orchestration
pipeline. According to the current project implementation and prior
successful local execution, the intended stages are:

1.  Load experiment configuration, verified pool, and required
    artifacts.
2.  Ensure the required source Student checkpoint exists.
3.  Compute Student NLL scores when required by the method/round.
4.  Estimate learnability values (Lproxy) using the method’s prescribed
    reference set.
5.  Select trajectories according to B4 or B5.
6.  Write train_set and selection/protocol logs.
7.  Validate the train set and selection constraints.
8.  Train the Student for the round and save the LoRA
    adapter/checkpoint.
9.  Evaluate the resulting Student on D_dev.
10. Save evaluation predictions and summary.

The exact stages and filenames are controlled by the checked-out
scripts/config. Before the official run, inspect: python
scripts/run_b4_b5.py –help python scripts/validate_experiment_config.py
–frozen python scripts/test_b4_b5_protocol.py

Do not assume a stage succeeded merely because the terminal printed a
start message. Require the final completion status, checkpoint, train
log, evaluation output/summary, and protocol validation.

======================================================================
3. PURPOSE OF B4 AND B5 IN THE PAPER
======================================================================

B4: Static learnability-based selection. - Uses learnability estimated
from S0. - Ranks eligible verified trajectories by descending Lproxy. -
Ties are broken by ascending trajectory_id. - The ranking is walked
across rounds. - A trajectory is not repeated across B4 rounds. - A
trajectory skipped because of the per-problem cap in one round can
remain eligible for a later round. - B4 is the static learnability-based
comparison method.

B5: Dynamic learnability-based selection. - Re-estimates learnability at
the current Student checkpoint for the relevant round. - Uses the
current checkpoint’s NLL scores to calculate Lproxy. - Ranks candidates
by descending Lproxy; ties use ascending trajectory_id. - Previously
selected trajectories may be selected again in later rounds, according
to the approved project decision. - Previously trained IDs are excluded
from the reference set used to estimate ell_star/sigma, but Lproxy is
still computed for all eligible candidates. - B5 tests whether
dynamically updating learnability as the Student evolves improves
selection compared with static B4.

Scientific comparison: - B5 vs B4 is the primary comparison. - The
experiment tests whether adapting trajectory selection to the current
Student’s learnability is more effective than keeping the S0-based
ranking fixed. - Seeds 13, 42, and 2026 provide repeated runs for
assessing robustness across random initialization/training variation. -
Three rounds allow analysis of how selection and Student performance
evolve over iterative distillation.

Do not claim that B5 is superior until the final evaluation and
statistical analysis support that conclusion.

12. TROUBLESHOOTING
======================================================================

If CUDA OOM: - Stop and inspect logs and GPU memory. - Do not silently
change batch size, sequence length, precision, or training config. - Any
protocol-affecting adjustment requires team approval and
documentation. - Confirm whether the run completed and whether a valid
checkpoint was saved before retrying.

If SSH disconnects: - Reconnect to the same running Pod. - Use tmux
attach -t kltn. - If Pod was stopped/restarted, tmux process may be
gone; inspect artifacts and rerun only after validating state.

If Pod is terminated or GPU unavailable: - Create a compatible Pod in
the same data center. - Attach the existing Network Volume. - Confirm
/workspace is mounted. - Inspect logs/checkpoints before resuming. -
Never assume an interrupted training process can resume from the last
step; the orchestrator may need to restart the round, and existing
partial artifacts must be inspected first.

If storage is full: - Check df -h and du -sh. - Do not delete
checkpoints or input data blindly. - Back up first and identify
safe-to-remove caches/temp files.

If a round reports COMPLETE but expected artifacts are absent: - Treat
it as incomplete. - Inspect the run log and validator output. - Do not
proceed to the dependent round.
